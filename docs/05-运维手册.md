# TodoList 运维手册

## 1. 运维范围

本文档面向 CCE、SWR、TDSQL、内网 DNS 和 Ingress 运维人员。应用部署在同一命名空间：

~~~text
命名空间：todo-internal
前端 Deployment：todo-frontend
后端 Deployment：todo-backend
数据库迁移 Job：todo-migration
前端 Service：todo-frontend
后端 Service：todo-backend
Ingress：todo-internal
~~~

实际命名空间、域名、镜像地址和 Ingress Class 以交付参数表为准。

## 2. 日常健康检查

~~~powershell
kubectl -n todo-internal get pods
kubectl -n todo-internal get deployments,services,ingress
kubectl -n todo-internal rollout status deployment/todo-backend
kubectl -n todo-internal rollout status deployment/todo-frontend
~~~

在企业内网执行：

~~~powershell
curl.exe -i https://[内网域名]/health
curl.exe -i https://[内网域名]/api/health
~~~

如果使用 HTTP，将 https 改为 http。两个健康接口应返回 HTTP 200。

## 3. 日志和故障定位

### 查看日志

~~~powershell
kubectl -n todo-internal logs deployment/todo-backend --tail=200
kubectl -n todo-internal logs deployment/todo-frontend --tail=200
kubectl -n todo-internal logs job/todo-migration
~~~

### 查看 Pod 事件

~~~powershell
kubectl -n todo-internal describe pod -l app.kubernetes.io/name=todo-backend
kubectl -n todo-internal describe pod -l app.kubernetes.io/name=todo-frontend
kubectl -n todo-internal get events --sort-by=.lastTimestamp
~~~

### 常见故障判断

| 现象 | 处理顺序 |
|---|---|
| Pod Pending | 检查节点资源、调度约束和资源配额 |
| ImagePullBackOff | 检查 SWR 地址、标签、镜像拉取 Secret 和节点网络 |
| 后端 CrashLoopBackOff | 查看后端日志，重点检查 TDSQL、JWT Secret 和环境变量 |
| Migration Job 失败 | 查看 Job 日志，检查 TDSQL 地址、白名单、权限和迁移历史 |
| 前端 200 但 API 失败 | 检查 /api Ingress 路由、后端 Service 和后端 Pod |
| 登录后立即失效 | 检查 HTTPS 与 APP_AUTH_SECURE_COOKIE 是否匹配，以及所有后端副本 JWT Secret 是否一致 |

## 4. 重启和恢复服务

优先使用滚动重启，不要直接删除全部 Pod：

~~~powershell
kubectl -n todo-internal rollout restart deployment/todo-backend
kubectl -n todo-internal rollout restart deployment/todo-frontend
kubectl -n todo-internal rollout status deployment/todo-backend --timeout=10m
kubectl -n todo-internal rollout status deployment/todo-frontend --timeout=10m
~~~

如果只有一个 Pod 异常，可先查看事件和日志，再删除单个异常 Pod，让 Deployment 自动补齐：

~~~powershell
kubectl -n todo-internal delete pod [异常Pod名称]
~~~

不要通过删除数据库 Pod 或删除 TDSQL 数据库来处理应用故障。

## 5. 配置修改

### ConfigMap 修改

修改 deploy/cce/configmap.yaml 后执行：

~~~powershell
kubectl apply -f .\deploy\cce\configmap.yaml
kubectl -n todo-internal rollout restart deployment/todo-backend
kubectl -n todo-internal rollout status deployment/todo-backend --timeout=10m
~~~

### Secret 修改

修改生产 Secret 前必须确认变更内容和审批记录：

~~~powershell
kubectl apply -f .\deploy\cce\secret.yaml
kubectl -n todo-internal rollout restart deployment/todo-backend
~~~

JWT Secret 变更会使原有 JWT 无法继续使用，所有用户需要重新登录。数据库密码变更前必须先在 TDSQL 侧同步修改账号密码，并安排维护窗口。

## 6. 扩缩容和资源调整

当前前后端 Deployment 默认各 2 个副本。临时扩容：

~~~powershell
kubectl -n todo-internal scale deployment/todo-backend --replicas=3
kubectl -n todo-internal scale deployment/todo-frontend --replicas=3
kubectl -n todo-internal get pods
~~~

临时 scale 不会修改 YAML，下一次 apply 可能恢复清单中的副本数。正式调整应同时修改 backend.yaml 或 frontend.yaml，并重新提交版本。

后端每个副本默认最多 10 个数据库连接。扩容前应确认 TDSQL 最大连接数和企业配额能够承受：

~~~text
最大连接数约等于后端副本数 × DB_POOL_MAX_SIZE
~~~

## 7. 版本迭代

标准顺序：

1. 固定 Git commit 和镜像标签。
2. 构建并推送前后端镜像。
3. 如果有数据库变更，先备份 TDSQL。
4. 执行 migration Job。
5. 确认 Job Complete。
6. apply 后端和前端 Deployment。
7. 观察滚动更新和健康检查。
8. 完成功能和权限验收。

~~~powershell
kubectl apply -f .\deploy\cce\backend.yaml
kubectl apply -f .\deploy\cce\frontend.yaml
kubectl -n todo-internal rollout status deployment/todo-backend --timeout=10m
kubectl -n todo-internal rollout status deployment/todo-frontend --timeout=10m
~~~

详细流程见 CCE_TDSQL_部署及迭代说明书.md。

## 8. 回滚

应用版本回滚：

~~~powershell
kubectl -n todo-internal rollout undo deployment/todo-backend
kubectl -n todo-internal rollout undo deployment/todo-frontend
kubectl -n todo-internal rollout status deployment/todo-backend
kubectl -n todo-internal rollout status deployment/todo-frontend
~~~

数据库迁移是向前的。不能只回滚应用镜像而假定数据库会自动回滚。数据库回退必须使用备份或由 DBA 制定兼容性方案。

## 10. 安全和权限

- 生产 Secret 只授予必要的运维和安全人员。
- 不在日志、工单和聊天中发送密码。
- 不把 secret.yaml 提交 Git。
- 定期轮换数据库密码、JWT Secret 和 TLS 证书。
- 停用离职或不再使用的账号。
- 保留至少一个启用的管理员。
- CCE Service 保持 ClusterIP，Ingress 使用内网 ELB。
