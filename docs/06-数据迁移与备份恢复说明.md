# TodoList 数据迁移与备份恢复说明

## 1. 适用范围

本文档适用于从旧 TodoList 原型数据库迁移到当前 Spring Boot + TDSQL 版本。首次生产迁移前必须由 DBA 备份数据库，并安排停写窗口。

## 2. 迁移前检查

迁移负责人应确认：

- 已取得旧数据库完整备份。
- 已确认旧应用停止写入。
- 已确认 TDSQL 版本和 MySQL 兼容性。
- 已创建目标数据库和应用账号。
- CCE 到 TDSQL 的网络、端口和白名单已放通。
- 已将真实数据库密码写入 CCE Secret，不写入 Git。
- 已确认 migration Job 使用目标后端镜像。
- 已记录旧任务数量、用户数量和分类数量。

建议在迁移前执行只读统计并保存结果：

~~~sql
SELECT COUNT(*) AS task_count FROM tasks;
SELECT COUNT(*) AS user_count FROM users;
SELECT COUNT(*) AS category_count FROM task_categories;
~~~

如果旧数据库还没有 users 或 task_categories 表，应只执行能够成功读取的统计语句，并记录“旧表不存在”。

## 3. 旧数据字段映射

### 3.1 任务字段

| 旧字段 | 新字段 | 处理方式 |
|---|---|---|
| id | id | 尽量保留原 ID |
| title | title | 保留标题，空标题需要人工处理 |
| startTime | start_date | 转换为 DATE；为空时使用 endTime 或当天日期 |
| endTime | deadline | 转换为 DATE；为空时使用 start_date 或当天日期 |
| assignee | legacy_assignee | 保存原始负责人姓名 |
| 原负责人姓名 | assignee_id | 尝试匹配新用户的 display_name 或 username |
| 原分类 | category_id | 首期统一归入“未分类” |
| status | status | 转为 NOT_STARTED、IN_PROGRESS 或 COMPLETED |
| progress | progress | 限制在 0 到 100；100 自动为 COMPLETED |
| 无 | version | 默认 0 |
| 无 | created_by_id | 允许为空，后续新任务记录创建人 |

### 3.2 用户和负责人

系统初始化 admin、member1、member2、member3、member4。旧任务中的负责人姓名会尝试匹配：

1. 新用户 display_name。
2. 新用户 username。

无法匹配的负责人会保留在 legacy_assignee 字段中，assignee_id 保持为空，由管理员后续处理。

### 3.3 分类

旧任务首期统一放入“未分类”：

- 分类名称：未分类。
- 默认颜色：#64748B。
- 默认排序：0。
- 默认状态：启用。

## 4. Flyway 迁移内容

迁移文件位于：

~~~text
backend/src/main/java/db/migration/V1__TeamTodoSchema.java
backend/src/main/java/db/migration/V2__AddUserSessionVersion.java
~~~

V1 负责：

- 创建 users。
- 创建 task_categories。
- 创建或升级 tasks。
- 增加旧任务的日期、状态、进度、负责人和版本字段。
- 创建“未分类”分类。
- 建立任务查询索引。

V2 负责：

- 为 users 增加 session_version。
- 为已有用户设置默认值 0。

## 5. 执行迁移

首次部署时：

~~~powershell
kubectl apply -f .\deploy\cce\migration-job.yaml
kubectl -n todo-internal wait --for=condition=complete job/todo-migration --timeout=10m
kubectl -n todo-internal logs job/todo-migration
~~~

确认 Job 完成后检查数据库：

~~~sql
SHOW TABLES;
DESCRIBE users;
DESCRIBE task_categories;
DESCRIBE tasks;
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
~~~

迁移 Job 使用 APP_BOOTSTRAP_ENABLED=false，不创建初始化用户。后端 Deployment 启动时再根据配置创建不存在的初始化用户。

普通版本发布不应重复执行同一个已完成的 Job。只有新增数据库迁移版本时，才应创建新的迁移 Job。

## 6. 迁移后核对

至少核对：

- 旧任务数量和新任务数量。
- 标题是否完整。
- 开始日期和截止日期是否合理。
- 进度是否全部在 0 到 100。
- 100% 任务是否为 COMPLETED。
- 无法匹配的负责人数量。
- “未分类”任务数量。
- 原任务 ID 是否保留。
- 新增用户是否可以登录。

## 7. 备份要求

### 迁移前

1. 停止旧应用写入。
2. 使用 TDSQL 控制台或企业标准工具创建全库备份。
3. 保存备份时间、备份 ID、数据库名和责任人。
4. 在测试数据库恢复一次，确认备份可用。

### 日常

由 DBA 按企业策略配置自动备份。交付时填写：

## 8. 恢复流程

恢复不是普通应用重启操作，必须由 DBA 审批和执行。

### 推荐恢复顺序

1. 通知用户停止操作。
2. 停止或隔离后端写入流量。
3. 保留故障数据库和当前日志，不直接覆盖删除。
4. 选择恢复点，优先恢复到独立测试数据库。
5. 在测试数据库验证 users、task_categories、tasks 和登录。
6. 由 DBA 制定正式切换方案。
7. 恢复后端服务并执行功能验收。
8. 记录数据丢失时间范围和恢复结果。

### 恢复后验收

- 管理员可以登录。
- 普通成员可以登录。
- 甘特图任务数量合理。
- 任务日期、负责人、分类和进度正确。
- 新增、编辑和查询任务正常。
- 分类和用户状态正常。

不要在没有备份和审批的情况下执行 DROP DATABASE、TRUNCATE TABLE 或直接覆盖生产数据库。

## 9. 迁移失败处理

如果 Job 失败：

1. 查看 Job 日志。
2. 记录 Flyway 失败版本和数据库错误。
3. 检查数据库连接、账号权限、表结构和 TDSQL 白名单。
4. 不要重复执行大量修改 SQL。
5. 由 DBA 根据备份和 flyway_schema_history 判断是否需要恢复。
6. 修正问题后使用新的迁移镜像或迁移脚本重新执行。

Flyway 迁移默认向前执行，应用镜像回滚不会自动撤销数据库结构变更。
